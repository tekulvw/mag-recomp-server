# Knife death notifications

An admitted retail on-foot knife hit publishes the existing death notification
when it first collapses a living human or kills a represented bot. It uses
Weapon source type 2 and the knife's actual equipment index from the selected
kit. Swipe damage kind 3 remains distinct from that notification source type.

The native Swipe branch rejoins the common hit metadata path before the Weapon
source and signed equipment-index stores. The server selects the knife catalog
from the already-admitted melee profile; it does not require a firearm row for
the knife or infer a weapon kind from its numeric ID. Ordinary firearms keep
their existing catalog validation and firearm-only accounting.

Notification planning and publication reuse the current participant identity,
life-generation and record-before-commit checks. The current human members of
the attacker's and victim's actual squads each receive the notice once. Head
flags use the configured body-region mapping. A friendly kill can notify while
retaining its existing friendly-kill statistic and no enemy-kill XP.

An incapacitated human's initial collapse owns the death notice. Subsequent
finishing damage or bleed-out does not replay it. Nonlethal damage, an invalid
hit and a failed evidence record do not publish a new notice. Mounted weapon
and victim admission remains with its separate qualified paths.

Synthetic native-event regressions use a knife-only combat catalog and assert
literal application bytes, recipient filtering, incapacitation/finishing,
terminal death, nonlethal hits and rollback. Their invented tuning is not a game
preset. These checks and the original-file metadata proof establish source
behavior; a native live match must still qualify the displayed knife kill feed.
Melee targeting, origin/range/LOS authority and cadence remain separate work.
Releases require the human maintainer's live-match review and manual action.
