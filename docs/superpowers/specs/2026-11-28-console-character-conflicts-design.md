# Console character-name conflicts

Verified Sony sessions may create a character when their requested internal name belongs to another account. The Sony-opted-in store API also assigns a safe name for a noncolliding 32-byte request, preserving the original as an alias; inbound create wire messages retain their existing 31-byte CString limit. Existing portal/development creation continues to return NameTaken. Never rename, overwrite or select a foreign character.

Store a nullable ConsoleRequestedName on the assigned character, atomically with creation in JSON and PostgreSQL. Only live aliases reserve an owner-scoped, case-insensitive key. An exact retry must match the original request and canonical NP identity. Soft deletion releases aliases and slots; selection ignores deleted rows. Restore validates its final chosen name (including a moved-aside fallback) against live aliases of the same owner and the 31-byte record limit, refusing unsafe names before dry-run/apply mutation or backup. Lists return the assigned name.

Generate at most 16 ASCII candidates from the requested prefix, an unpredictable 96-bit random discriminator and the existing !slot suffix, at most 31 bytes to fit the full-record CString (within the requested 32-byte limit). The persisted alias supplies retry stability; public owner/request text cannot predict the fallback names. One pool is generated after request validation and reused across all transaction retries, so the entire logical request considers at most 16 names. The durable transaction checks all candidates; database unique indexes and existing bounded conflict retries cover races. Exhaustion returns NameTaken. Sony provider state is retained from successful authentication; callers explicitly opt in, rather than inferring trust from an online ID.

Approaches: renaming the foreign holder is unsafe; process-only aliases lose reconnects. A nullable durable character column fits both existing backends and existing transaction/soft-delete behavior without a second identity store. Alias lookup is exact and limited to the authenticated owner in MAS, including selected-character checks for character data. NP identity normalization remains unchanged.

Offline acceptance covers portal/development refusal, Sony retry and ownership, suffix and length bounds, bounded database conflict retries, JSON reload and deletion reuse, PostgreSQL migrations/concurrency/persistence and both wire profiles through MAS and MLS handoff. Hardware compatibility remains unverified. No releases, deployment or real accounts.
